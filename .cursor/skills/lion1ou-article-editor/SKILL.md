# Article Editor

主编式文章生产 skill。它负责把一个主题、资料包、链接、笔记或已有草稿变成博客优先的母版文章。母版文章是后续公众号、小红书和其他渠道改写的内容源，不直接承担渠道改写和发布。

## 边界

适用场景：

- 从一句想法、资料、链接或草稿生成文章。
- 写当前 Hexo 博客的技术类、生活类、AI、前端、茶叶、NAS 等主题文章。
- 需要选题定位、资料补全、三方向提纲、草稿、自评估、合并成稿。
- 需要一个后续可交给 `lion1ou-article-channel` 的稳定母版。

不适用场景：

- 把母版文章改写成公众号、小红书或其他渠道成品。改用 `lion1ou-article-channel`。
- 执行博客部署、公众号草稿创建、小红书发布。改用 `lion1ou-article-publish`。
- 只做排版格式修复。优先使用 `baoyu-format-markdown`。

## 工作原则

- 先确定读者和文章价值，再写正文。
- 能查证的事实不要靠猜。技术、AI、NAS、产品、版本、趋势类内容默认需要资料补全。
- 生活、茶叶和个人经验类文章保留个人判断，不把文章写成百科。
- 必须先给三种方向的提纲，不能直接起草。
- 用户没有确认提纲前，不写完整草稿。
- 自评估里仍有高风险事实缺口时，不输出最终母版。
- 所有过程产物都服务于最终成稿，避免生成无用中间文档。

## 用户输入规则

需要用户选择时，优先使用当前运行时的结构化提问工具；没有时使用简短编号问题。

只问会改变方向的问题。默认最多先问 1 个关键问题；其他信息先基于上下文做保守假设，并在产物中标明。

## 目录结构规范

所有文章生产过程都必须落在一个“文章工作区”里，避免文件散落。

默认工作区：

```text
articles/<YYYYMMDD>-<topic-slug>/
```

命名规则：

- `<YYYYMMDD>` 使用创建日期。
- `<topic-slug>` 使用小写英文 kebab-case，只包含 `a-z`、`0-9`、`-`。
- 中文主题要翻译核心含义，例如 `20260528-ai-writing-flow`、`20260528-fuding-white-tea`。
- 用户指定路径时，仍要在该路径下保持同样结构。

标准结构：

```text
articles/<YYYYMMDD>-<topic-slug>/
├── meta.md
├── research.md
├── outline-a.md
├── outline-b.md
├── outline-c.md
├── draft.md
├── editorial-review.md
├── master.md
├── assets-brief.md
├── assets/
│   ├── cover/
│   ├── inline/
│   └── refs/
├── channels/
│   ├── blog/
│   ├── wechat/
│   └── xhs/
└── publish/
```

路径约束：

- `articles/` 是文章生产工作区；`source/` 是 Hexo 工作目录，两者必须区分。
- `research.md`、提纲、草稿、自评估、母版和素材简报都放在文章工作区根目录。
- 生成图片、截图、参考图等通用素材放在工作区 `assets/`，不要散落在仓库根目录、`docs/` 或 `source/`。
- 渠道成品只放在 `channels/<channel>/`，由 `lion1ou-article-channel` 继续维护。
- 发布记录只放在 `publish/`，由 `lion1ou-article-publish` 继续维护。
- `lion1ou-article-editor` 不写入 `source/_drafts/`、`source/_posts/` 或 `source/images/`。
- 不覆盖用户已有文件；如需覆盖，先备份为 `<name>.backup-YYYYMMDD-HHMMSS.<ext>`。

## 流程

开始后复制并维护这个进度：

```markdown
Article Editor 进度：
- [ ] 第 1 步：输入识别与选题定位
- [ ] 第 2 步：资料补全与事实检查
- [ ] 第 3 步：生成三方向提纲
- [ ] 第 4 步：用户选择或合并提纲
- [ ] 第 5 步：生成博客优先草稿
- [ ] 第 6 步：主编自评估
- [ ] 第 7 步：修订并输出母版文章
- [ ] 第 8 步：输出配图与渠道素材简报
```

### 第 1 步：输入识别与选题定位

先判断输入类型：

| 输入 | 处理方式 |
| --- | --- |
| 一句话主题 | 先问 1 个方向问题，再进入资料补全 |
| 链接或多链接 | 读取链接并整理来源，再提炼选题 |
| 笔记或资料包 | 提炼核心观点、素材缺口和潜在文章方向 |
| 已有草稿 | 识别文章问题，保留可用内容，再进入三提纲 |
| 明确标题和大纲 | 检查是否仍需要资料补全，然后生成三方向变体 |

必须形成这些元数据：

- `topic`: `frontend`, `ai`, `tea`, `life`, `nas`, or another explicit topic.
- `articleType`: `tutorial`, `experience`, `opinion`, `review`, `note`, `story`, `mixed`.
- `audience`: 目标读者。
- `sourceLevel`: `personal`, `researched`, `mixed`.
- `blogCategory`: 优先沿用当前博客分类，如 `前端技术`、`JavaScript`、`Cordova` 等；没有合适分类时给出建议。
- `tags`: 3 到 6 个标签，兼顾主题和检索。
- `successCriteria`: 读者读完后应该理解、获得或行动的结果。

如果用户只给了宽泛主题，优先问：

```text
这篇文章更想写成哪类：A. 实用教程 B. 个人经验 C. 观点洞察 D. 先由我基于资料推荐？
```

### 第 2 步：资料补全与事实检查

以下情况必须使用 `lion1ou-search-tools`：

- 主题涉及技术、AI、NAS、工具、产品、标准、API、版本或时效信息。
- 用户提供 URL，需要读取或提炼。
- 文章包含可被事实验证的对比、趋势、价格、性能、健康功效或产品能力。
- 需要引用外部资料支撑结论。

以下情况可不搜索，但要说明依据：

- 纯个人记录、生活感受、随笔。
- 用户明确要求基于个人经验写，不需要查资料。
- 已提供足够可信资料，且文章不包含额外事实判断。

生活和茶叶类文章的判断：

- 写冲泡、产地、工艺、年份、价格、健康功效时要查证。
- 写个人体验、茶席记录、生活感受时以个人表达为主，只做轻量补充。

输出 `research.md`：

```markdown
# 资料整理

## 用户输入摘要
- ...

## 已确认事实
- [事实]：来源或用户提供依据

## 可用来源
- [标题](url)：用途

## 仍需确认
- 没有则写“无”

## 需要谨慎表述的点
- [缺少依据、容易夸大或可能过时的说法]
```

不能把未证实信息写成确定事实。时间敏感内容要写清检索日期或资料时间。

### 第 3 步：生成三方向提纲

必须生成 3 个真正不同的方向，不能只是换标题：

- A. 实用教程型：步骤、清单、方法、实施路径。
- B. 个人经验型：经历、选择过程、踩坑、反思。
- C. 观点洞察型：判断、趋势、对比、框架、反常识。

每份提纲都要包含：

- 2 到 3 个标题候选。
- 一句话核心承诺。
- 目标读者。
- 文章结构，至少到二级标题。
- 关键素材和事实依据。
- 素材缺口或风险。
- 适合渠道：`blog`、`wechat`、`xhs` 或 `mixed`。
- 推荐指数和理由。

分别保存为 `outline-a.md`、`outline-b.md`、`outline-c.md`。

### 第 4 步：用户选择或合并提纲

硬门禁：用户未选择或确认前，不能写完整草稿。

让用户选择：

- 直接使用 A、B 或 C。
- 合并多个方向。
- 修改某个方向后再写。
- 用户给出自定义方向。

合并时先写清：

```markdown
## 合并决策
- 保留 A 的：
- 保留 B 的：
- 保留 C 的：
- 删除或弱化的：
- 最终文章承诺：
```

确认后再进入草稿。

### 第 5 步：生成博客优先草稿

草稿优先服务当前 Hexo 博客，同时保留足够深度，便于后续改写到公众号和小红书。

默认保存为 `draft.md`。使用这个 frontmatter：

```yaml
---
title: ""
toc: true
comments: true
categories: ""
tags:
  - ""
date: ""
photos:
description: ""
topic: ""
articleType: ""
audience: ""
sourceLevel: ""
channels:
  - blog
status: draft
---
```

正文规则：

- 标题只放在 frontmatter，不在正文重复 H1。
- 开头要在 3 到 5 段内说明读者为什么要读。
- `<!--more-->` 放在开头钩子或第一小节后。
- 技术文章必须给具体示例、命令、代码、版本或约束，不写伪代码。
- AI/NAS/工具文章要区分事实、体验和判断。
- 生活类文章保留第一人称、场景细节和个人判断。
- 茶叶类文章区分个人口感、产区工艺事实和购买建议。
- 研究资料影响结论时，要保留引用或来源说明。
- 不写“本文将介绍”这类弱开头，直接给问题、场景或判断。

### 第 6 步：多模型对抗式 review

成稿前必须通过多模型对抗式 review，不能只做单模型自评。至少使用 3 个相互独立的审稿视角：

| 视角 | 重点 |
| --- | --- |
| 事实审计 | 查无来源事实、宣传口号、过度推断、时效性数据和高风险表述 |
| 结构表达 | 查开头钩子、结构推进、重复、资料拼接感、信息密度和博客可读性 |
| 读者质疑 | 模拟挑剔读者，查承诺是否兑现、是否空泛、是否有实操价值、是否适合后续渠道改写 |

优先使用不同模型或不同审稿代理执行；如果运行环境无法调用多个模型，必须在 `editorial-review.md` 中说明降级原因，并用三个明确分离的审稿人格完成对抗式审查。

每个审稿视角都必须给出：

- `findings`：按严重程度排序的问题。
- `impact`：问题会怎样影响准确性、可信度、可读性或发布效果。
- `fix`：明确到段落、小节或句子的修订动作。
- `verdict`：`pass`、`revise` 或 `block`。

写入 `editorial-review.md`：

```markdown
# 主编自评估

## 多模型对抗式 review 摘要
- 使用模型或审稿视角：
- 总体裁决：pass / revise / block
- 必须修订的问题：

## 事实审计 review
- Finding:
- Impact:
- Fix:
- Verdict:

## 结构表达 review
- Finding:
- Impact:
- Fix:
- Verdict:

## 读者质疑 review
- Finding:
- Impact:
- Fix:
- Verdict:

## 主编裁决
- 采纳：
- 不采纳：
- 降级表述：
- 删除：
- 补充来源：

## 准确性
- 事实是否有来源？
- 是否存在版本、时间、价格、健康功效等高风险表述？

## 原创性
- 哪些内容来自个人经验、判断或独特组织？
- 哪些段落像通用资料拼接？

## 结构
- 逻辑线是否清晰？
- 是否有缺失、重复或跳跃？

## 信息密度
- 哪些地方太空？
- 哪些地方太密？

## 可读性
- 标题、段落、例子是否易读？
- 是否需要列表、表格或代码块？

## 博客适配
- frontmatter 是否完整？
- 分类、标签、摘要、`<!--more-->` 是否合适？

## 修订计划
- [明确到段落或小节的修改动作]
```

任一审稿视角给出 `block` 时，不能输出最终母版；必须先补资料、删除问题内容或降级表述。任一审稿视角给出 `revise` 时，必须在 `editorial-review.md` 记录主编裁决，并将修订落实到 `master.md` 后才能完成。

### 第 7 步：修订并输出母版文章

根据自评估和用户反馈修订，保存为 `master.md`。

母版要求：

- 可以独立作为博客文章发布。
- 信息完整，但不过度迎合公众号或小红书。
- 事实、观点、经验边界清楚。
- 标题、摘要、分类、标签可直接被 `lion1ou-article-channel` 读取。
- 图片需求清楚，但不强制已经生成图片。

### 第 8 步：输出配图与渠道素材简报

写 `assets-brief.md`：

```markdown
# 配图与素材简报

## 封面图
- 用途：
- 视觉隐喻：
- 是否带标题文字：
- 推荐风格：
- 避免元素：

## 正文配图
- 位置：
- 目的：
- 建议类型：
- 是否需要真实截图或示意图：

## 渠道机会
- 博客：
- 公众号：
- 小红书：
```

该文件用于后续交给 `lion1ou-article-channel` 调用 `baoyu-cover-image`、`baoyu-article-illustrator` 或 `baoyu-xhs-images`。

## 输出位置

除非用户明确指定路径，否则使用根目录 `articles/<YYYYMMDD>-<topic-slug>/`。`lion1ou-article-editor` 只负责工作区内的母版产物，不直接写入 `source/`。

博客最终发布路径由 `lion1ou-article-publish` 处理。博客发布阶段只把 Markdown 写入 Hexo 的 `source/_posts/`，图片仍留在生产工作区，由 `lion1ou-article-publish` 上传 CDN 后替换为 CDN 链接。

```text
source/_posts/<YYYY-MM>/<YYYYMMDD>-<topic-slug>.md
```

## 完成报告

结束时报告：

- 母版文章路径。
- 选择或合并了哪个提纲方向。
- 使用了哪些资料来源，是否还有不确定点。
- 博客分类和标签。
- 生成了哪些支持文件。
- 下一步建议使用 `lion1ou-article-channel`。

## 稳定产出检查

完成前逐项检查：

- 已生成 `research.md`，或明确说明为什么不需要资料补全。
- 已生成 3 个方向提纲。
- 用户已确认提纲方向。
- 已生成 `draft.md`、`editorial-review.md`、`master.md`、`assets-brief.md`。
- `editorial-review.md` 已记录多模型对抗式 review、主编裁决和已执行的修订动作。
- 所有过程文件位于同一个文章工作区。
- `master.md` 有完整 frontmatter。
- `master.md` 不包含未解决占位符、`TODO`、`待定`。
- 技术和事实性内容没有无来源的强结论。
