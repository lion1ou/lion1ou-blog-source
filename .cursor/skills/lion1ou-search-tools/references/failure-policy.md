# Failure Policy

## 原则

先区分失败类型，再决定重试、降级还是阻断。不要把所有失败都当成“再搜一次”。

## 失败分级

| 类型 | 典型信号 | 处理策略 |
|---|---|---|
| 可重试 | 单个搜索源超时、暂时性 5xx、偶发空结果 | 换源或重试 1-3 次，保留已成功结果 |
| 可降级 | 结果偏少、正文抓取失败、部分页面不可读 | 切换到其他抓取路径，并明确说明限制 |
| 阻断 | 权限不足、登录必需、关键依赖缺失、所有路径都失败 | 立即停止，返回原因和下一步建议 |

## 搜索阶段

### 单引擎失败

- 不要整次搜索直接失败
- 保留其他引擎结果
- 在 `notes` 里记录失败源

### 所有引擎失败

返回：

```json
{"error":"所有搜索源均失败"}
```

然后：
- 如果用户给的是 URL，改走 `read-url`
- 如果只是普通搜索，提示当前搜索源全部失败
- 如果是研究任务，标记研究受阻，不要编造结论

## URL 读取阶段

### `web_fetch` 失败

失败信号：
- 空白页
- 403
- CAPTCHA
- 骨架 HTML

处理顺序：
1. 转 `opencli`
2. 仍失败时，判断是否属于反爬站
3. 是反爬站则运行内置免费抓取脚本 `python3 scripts/fetch.py <url>`
4. 还需要交互、登录或截图时转 `agent-browser` / browser

### 反爬或公众号

直接运行 `python3 scripts/fetch.py <url>`，不要在 `web_fetch` 上反复重试。已知站点与限制见 `references/antibot-sites.md`。

## 研究阶段

`deep-research-pro` 使用 `lion1ou-search-tools` 时必须遵守：
- 找不到来源就写 `insufficient data found`
- 只有单一来源支持的观点，标记为未充分验证
- 子问题失败时保留缺口说明，不得跳过并假装完整

## 浏览器阶段

以下情况属于阻断或需要人工确认：
- 需要登录
- 需要验证码
- 涉及发帖、支付、删除等敏感动作

处理：
- 先向用户说明原因
- 获得确认后再继续
- 无法自动完成验证码时明确要求人工介入

## 结果说明模板

### 可重试

`部分搜索源失败，已用其余引擎结果继续。`

### 可降级

`标准抓取失败，已降级到备用抓取路径；结果可能缺少部分格式或动态内容。`

### 阻断

`任务被阻断：需要登录/权限/依赖修复后才能继续。当前未执行后续高风险动作。`
